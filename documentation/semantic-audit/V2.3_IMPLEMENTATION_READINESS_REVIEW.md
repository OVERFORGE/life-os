## 2. Review of Corrections Across V2.2 Sections

### 2.1 Correction 1: Fast Execution and Multi-Operation Routing
- **V2.2 Citation:** Section 7 (`evaluateFastExecutionEligibility`, lines 434–436) and Section 8.1.
- **Why Necessary:**
  - In V2.2, Gate 1 rejected every turn where `operations.length !== 1` as `CLARIFICATION_REQUIRED`. This rendered the Independent Atomic Batch path completely unreachable in code and incorrectly prompted the user for clarification whenever multiple operations were requested.
- **Verification in V2.3:**
  - Section 5 of V2.3 establishes the `evaluateOperationalRouting()` gate.
  - Formally delineates six mutually exclusive categories:
    1. `SINGLE_ATOMIC_OPERATION` (Fast-path direct execution).
    2. `INDEPENDENT_OPERATION_BATCH` (Multi-operation turn without cross-step dependencies; executed directly without DAG planning latency).
    3. `COMPOSITE_WORKFLOW_DAG` (Multi-operation turn with data dependencies; routed to `DynamicWorkflowPlanner`).
    4. `CLARIFICATION_REQUIRED` (True ambiguity or missing payload; prompts user).
    5. `HUMAN_AUTHORIZATION_REQUIRED` (HITL approval / exclusive lock; HMAC-signed pending intervention).
    6. `UNREGISTERED_CAPABILITY` (Fail-closed unregistered tool).
  - Clarification is now strictly confined to genuine ambiguity or incomplete information.

### 2.2 Correction 2: Structural Workflow Dependency Detection
- **V2.2 Citation:** Section 8.2 (`requiresDynamicWorkflowPlanner`, lines 569–586).
- **Why Necessary:**
  - V2.2 evaluated data dependencies via string search across raw JSON (`payloadStr.includes("$ref:")`), which produced false positives on natural text, and relied on capability category heuristics (`desc?.category === "query"`), which falsely triggered DAG replanning even when query outputs were not consumed.
  - V2.2 also contained an operator-precedence bug (`desc?.category === "discovery" || desc?.category === "query" && idx < operations.length - 1`).
- **Verification in V2.3:**
  - Section 6 of V2.3 introduces `StructuralDependencyAnalyzer.ts`.
  - Replaces substring searches with recursive object traversal (`extractStepReferences`).
  - Evaluates explicit step dependencies (`op.dependencies`) and typed parameter references (`$ref:stepId.path` and `{"$ref": { stepId, path }}`).
  - Eliminates category-based heuristics: a query tool only triggers dynamic planning if another step in the turn explicitly consumes its output.

### 2.3 Correction 3: Complete Authoritative Execution Contract
- **V2.2 Citation:** Section 7 (ActionProposal generation, line 497).
- **Why Necessary:**
  - V2.2 defaulted all non-reversible actions to `atomic_single_doc`, misrepresenting external irreversible actions (e.g., sending emails, deleting remote files).
  - V2.2 did not explicitly isolate the validation responsibilities of each component, creating the danger of Supervisor duplicating kernel validation or trusting unvalidated model metadata.
- **Verification in V2.3:**
  - Section 4 of V2.3 explicitly maps out all nine pipeline stages and their authoritative owners:
    - Semantic Interpretation: `SemanticIntentInterpreter`
    - Entity Resolution: `AuthoritativeEntityResolver`
    - Structural Routing: `DynamicRouter` & `StructuralDependencyAnalyzer`
    - Schema Validation: `ActionPayloadSchemas` (Zod)
    - Capability Governance: `CapabilityRegistry`
    - Tenant Authorization: `ExecutionContext` / Security Context
    - Concurrency & Locks: `WorkerLeaseManager` / Resource Reservation
    - Preconditions & Fencing: Native Handlers (`__v` optimistic versioning)
    - Transactional Execution: `KernelCapabilityService` / `DurableOutboxDispatcher`
  - Reversibility is governed strictly by `CapabilityDescriptor.reversibility` (`atomic_single_doc`, `reversible_with_compensation`, or `irreversible_external`).
  - Model metadata is formally defined as untrusted proposal input.

### 2.5 Correction 5: Truthful Evidence & Verification Standards
- **V2.2 Citation:** Section 5 (Matrix, lines 362–364), Section 6, and Section 9.
- **Why Necessary:**
  - V2.2 labeled parameters like `LifeStateWeights` and `decayHalfLifeDays` as "empirically calibrated" without empirical telemetry data in the repository.
  - Upstream outage handling lacked a concrete retry and deduplication contract.
  - Custom signal logging lacked guarantees against data loss if schema registration failed.
- **Verification in V2.3:**
  - Section 7 refines the taxonomy into an Eight-Tier Taxonomy, accurately classifying `decayHalfLifeDays` as `[LIT-BASE]` (literature baseline) and `LifeStateWeights` as `[PROD-DEF]` (product default weights).
  - Section 8.1 defines the **Upstream Outage Preservation Lifecycle**, using `requestId`, `turnId`, `OutagePreservationRecord`, and kernel idempotency deduplication on retry.
  - Section 8.2 defines the **Dynamic Custom Signal Lifecycle**, guaranteeing zero data loss by persisting unindexed signals immediately to `DailyLog.customSignals` prior to asynchronous registration.
  - Section 9.2 introduces the **Decision Correctness Matrix**, penalizing eager execution on ambiguous inputs.
