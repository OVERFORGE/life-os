## 2. Section-by-Section Diff & Refinement Record

### Section 2: Permanent Semantic Architecture Constitution
- **Refinement:** Strengthened Article II (Authoritative Intelligence Ownership Boundaries).
  - Explicitly designated [`CapabilityRegistry`](file:///d:/PROGRAMMING/Projects/life-os/packages/execution-kernel/src/orchestration/capabilities/CapabilityRegistry.ts) as the **sole authority** on capability existence, execution contracts, reversibility, access modes, and approval requirements.
  - Formally prohibited competing capability definitions, secondary static dictionaries, and helper classification services.
  - Barred the Supervisor from maintaining internal classification dictionaries or secondary routing authorities.

### Section 3: Permanent Automated Architectural Enforcement Architecture
- **Refinement:** Shifted enforcement focus from syntax-matching to **behavioral ownership boundary protection**.
  - Added `RULE 1: [ARCH-BOUNDARY-SUPERVISOR]`, restricting `Supervisor.ts` imports to an authorized whitelist of canonical interfaces and facades. Moving an illegal regex or keyword parser to a helper file and importing it into `Supervisor` is blocked at the AST level.
  - Added `RULE 8: [ARCH-BOUNDARY-DISPATCH]`, establishing that no module outside `SemanticIntentInterpreter` may classify natural language intent or extract domain actions.
  - Clarified AST node visitors to inspect semantic behavior (e.g. inspecting assistant prose to mutate `actionType`), preventing bypasses through function renaming.

### Section 4: CI Protection & Governance Design (Protecting the Enforcement Itself)
- **Refinement:** Completely overhauled the tamper-resistance mechanism.
  - **Correction:** Removed claims that a repository-local hash alone was tamper-proof (since a PR can edit both code and local hashes).
  - **New Design:** Implemented a practical four-layer governance model:
    1. **CODEOWNERS Access Gate:** Enforces that any modification to enforcement scripts, tests, workflows, or exception files requires independent review from `@exe-architects`.
    2. **CI Base-Ref Execution Guard:** In CI pull request pipelines, if enforcement scripts are modified, the runner checks out and executes the linter from `origin/master` rather than the PR branch, ensuring that a feature branch cannot weaken the check that evaluates its own code.
    3. **Branch Protection:** `verify-semantic-architecture` is configured as a Strict Required Status Check with administrator enforcement.
    4. **Exception Linter:** Validates `.architectural-exceptions.json` with a hard limit of 5 active exceptions and a mandatory 30-day expiration TTL.

### Section 5: Fixed-Value & Behavioral Defaults Classification
- **Refinement:** Re-audited the fixed-value inventory into a **Seven-Tier Classification Taxonomy**.
  - Corrected parameters that were previously misclassified as mathematical invariants merely because they appeared in mathematical formulas (e.g., `decayHalfLifeDays = 21.0` was reclassified from mathematical invariant to `[EMP-CAL]` empirically calibrated parameter).
  - Explicitly separated genuine mathematical invariants (`[MATH-INV]` like Kahn's topological sort and circular trigonometry `atan2`) from technical constraints (`[TECH-CON]` like recursion stack limits).
  - Added explicit owners and rationale for every retained product default.
  - Reaffirmed the **explicit unknown semantics** principle: missing data must remain `undefined` rather than fabricated (e.g. unmeasured task duration remains `undefined` rather than defaulting to 30 minutes).

### Section 6: Rejection, Fallback, and Truthful Intent Preservation
- **Refinement:** Expanded the rejection and fallback audit across the production call graph.
  - Traced actual execution flows through `Supervisor`, `SemanticIntentInterpreter`, `DynamicRouter`, `EntityResolver`, `DynamicWorkflowPlanner`, and adapters.
  - Eliminated silent intent loss in upstream outages: Groq LLM service failures return explicit `ambiguityStatus: "UPSTREAM_OUTAGE"` with `system_error` events instead of silently masquerading as casual dialogue (`FB-01`).
  - Eliminated silent null returns when entity IDs fail resolution: returns structured clarification turns asking the user if they wish to create the missing entity (`FB-02`).
  - Formally established the **Truthful Outcome Principle**: every rejected, deferred, or ambiguous request must yield an explicit and truthful explanation.

### Section 7: Corrected Fast Execution Eligibility Gate
- **Refinement:** Re-engineered the single-turn fast execution gate to handle new-entity creation cleanly.
  - **Correction:** V2.1 erroneously required every operation to resolve an existing database entity ID. This would have broken valid creation operations (`create_task`, `create_goal`, `log_meal`).
  - **New Design:** Explicitly bifurcated Gate 7 into:
    - **Category A (New-Entity Creation):** Does NOT require a pre-existing `targetEntityId`. Requires valid Zod payload parameters and duplicate-policy validation.
    - **Category B (Existing-Entity Mutation):** Strictly requires `targetEntityId` resolved against MongoDB by `AuthoritativeEntityResolver`.
  - **Fail-Closed on Unknown Capabilities:** If a capability is not registered in `CapabilityRegistry`, the gate fails closed (`UNREGISTERED_CAPABILITY`). An unknown tool never becomes executable.
  - **HITL Precedence:** Authoritative descriptor properties (`requiresApproval`, `accessMode: "EXCLUSIVE_LOCK"`) strictly outrank model-generated risk classifications.

### Section 8: Semantic Workflow Planning (Data Dependencies vs Batches)
- **Refinement:** Overhauled dynamic workflow routing.
  - **Correction:** Removed the naive rule that triggered workflow planning whenever `operations.length > 1`.
  - **New Design:** Planning decisions are derived from **structural execution requirements**:
    - **Independent Atomic Batch:** Multiple operations without data dependencies (e.g. *"Reschedule workout to 6pm and log 8h sleep"*) execute directly as atomic kernel mutations without spawning a DAG planner.
    - **Composite Dynamic Workflow:** Operations with parameter references (`$ref:stepId.prop`), intermediate output flows, or observation preconditions route to `DynamicWorkflowPlanner`.

### Section 9: Generalization and Held-Out Testing Methodology
- **Refinement:** Separated open repository tests from unseen generalization testing.
  - **Tier A (Known Contract Tests):** Basic regression fixtures committed in the repository.
  - **Tier B (Held-Out Generalization Suite):** Parameterized dynamic generator running in CI across syntactic structures, lexical registers, speech noise, and multilingual code-switching.
  - **Decision Correctness:** Tests evaluate whether the system made the correct decision (including asking for clarification or reporting unavailable tools), rather than merely rewarding state mutation.
