## 2. Section-by-Section Diff & Refinement Record

### 2.1 Fast Execution Gate & Multi-Operation Routing
- **Location:** V2.2 Section 7 (`evaluateFastExecutionEligibility`) & Section 8.
- **Defect in V2.2:**
  - Gate 1 in `evaluateFastExecutionEligibility()` immediately returned `{ eligible: false, category: "CLARIFICATION_REQUIRED", rejectionCode: "NON_ATOMIC_TURN" }` whenever `operations.length !== 1`.
  - This made the **Independent Operation Batch** architecture described in Section 8 completely unreachable through the gate.
  - Furthermore, turns with multiple operations were mislabeled as requiring conversational clarification, conflating planner routing with conversational ambiguity.
- **Correction in V2.3:**
  - Replaced `evaluateFastExecutionEligibility()` with `evaluateOperationalRouting()`.
  - Formally established **six mutually exclusive operational categories**:
    1. `SINGLE_ATOMIC_OPERATION` (Fast-path single mutation).
    2. `INDEPENDENT_OPERATION_BATCH` (Multi-operation turn with zero inter-step dependencies; executed as an atomic batch without DAG synthesis).
    3. `COMPOSITE_WORKFLOW_DAG` (Multi-operation turn with inter-step data dependencies or intermediate outputs; routed to `DynamicWorkflowPlanner`).
    4. `CLARIFICATION_REQUIRED` (True semantic ambiguity, unresolvable entity reference, or missing required payload; halts execution and prompts user).
    5. `HUMAN_AUTHORIZATION_REQUIRED` (Authoritative HITL requirement or exclusive lock; creates HMAC-signed pending intervention).
    6. `UNREGISTERED_CAPABILITY` (Unregistered capability URN; fails closed).
  - Clarification is now strictly reserved for genuine conversational ambiguity and missing data, never for routing or batch partitioning.

### 2.2 Structural Workflow Dependency Detection
- **Location:** V2.2 Section 8.2 (`requiresDynamicWorkflowPlanner`).
- **Defect in V2.2:**
  - Evaluated data dependencies by string search across JSON payloads: `payloadStr.includes("$ref:")`. This was vulnerable to false positives (e.g. user entering the literal text `"$ref:"` in a note).
  - Used capability category heuristics: `desc?.category === "discovery" || desc?.category === "query" && idx < operations.length - 1`.
  - Contained an operator-precedence bug: `||` binds looser than `&&`, causing any discovery capability anywhere in the operations array to trigger the dynamic planner, even if no other step depended on its output.
- **Correction in V2.3:**
  - Implemented `StructuralDependencyAnalyzer.ts` with recursive AST/JSON object traversal (`extractStepReferences`).
  - Formally defined typed contracts for:
    - **Data Producers** (steps producing observable output in `StepOutputRecord`).
    - **Data Consumers** (steps containing typed `$ref` tokens referencing an upstream step).
    - **Explicit Dependencies** (`op.dependencies` array).
    - **Runtime Observations** (dynamic parameter bindings).
    - **Parallelizable Operations** (disjoint dependencies and non-conflicting shared resource locks).
  - Completely eliminated category-based heuristics. A query or discovery tool alone does not imply a dependency unless another operation in the turn explicitly consumes its output or declares a dependency upon it.

### 2.3 Authoritative End-to-End Execution Contract
- **Location:** V2.2 Section 7 (ActionProposal generation & execution boundaries).
- **Defect in V2.2:**
  - V2.2 line 497 assigned reversibility as: `reversibility: descriptor.isReversible ? "reversible_with_compensation" : "atomic_single_doc"`.
  - This incorrectly categorized all non-reversible actions as `atomic_single_doc`, which was dangerous for external irreversible actions (e.g., sending emails, deleting external resources, booking rides).
  - Did not clearly delineate where semantic interpretation ends, where validation occurs, and where kernel execution begins, creating the risk of Supervisor duplicating kernel checks or trusting model-generated metadata.
- **Correction in V2.3:**
  - Created Section 4: **Authoritative End-to-End Execution Pipeline**.
  - Established explicit single-owner boundaries across all nine stages: Semantic Interpretation, Entity Resolution, Structural Routing, Schema Validation, Capability Governance, Tenant Authorization, Concurrency/Locks, State Fencing, and Transactional Kernel Execution.
  - Specified that `CapabilityDescriptor.reversibility` is the sole authority for action reversibility (`atomic_single_doc`, `reversible_with_compensation`, or `irreversible_external`).
  - Enforced that model-generated metadata (such as `riskClass`) is treated as untrusted raw input that cannot override kernel registry contracts.

### 2.4 Accurate Architectural Enforcement Alignment
- **Location:** V2.2 Section 3 (`scripts/verify-semantic-architecture.ts` and CI Governance).
- **Defect in V2.2:**
  - The table in Section 3.1 declared eight architectural rules, but the accompanying linter script only implemented checks for Rules 1, 2, and 3, leaving Rules 4–8 unimplemented in the example code.
  - V2.2 did not clearly separate static AST checks, behavioral architecture tests, and external GitHub branch protection settings.
  - It described `.github/CODEOWNERS` and branch protection as if repository files could enforce themselves without external GitHub configuration.
- **Correction in V2.3:**
  - Provided a complete implementation of `scripts/verify-semantic-architecture.ts` covering AST-feasible checks across all eight rules (Rules 1–8).
  - Structured enforcement into **Four Explicit Layers**:
    1. Static AST Linter (`scripts/verify-semantic-architecture.ts`).
    2. Behavioral Architecture Tests (`src/testing/architecture/`).
    3. CI Base-Ref Immutable Execution Guard (`ci.yml` running linter from `origin/master`).
    4. External Repository Governance (GitHub Branch Protection, Strict Status Checks, and Administrator Enforceability).
  - Explicitly added the **Trust Boundary Notice** explaining that GitHub branch protection and required status checks must be configured in external repository settings.

### 2.5 Rigorous Verification & Evidence Standards
- **Location:** V2.2 Section 5, 6, and 9.
- **Defect in V2.2:**
  - In Section 5, parameters such as `LifeStateWeights` (formula weights) and `decayHalfLifeDays` were labeled as "empirically calibrated" (`[EMP-CAL]`) despite lacking empirical telemetry studies in the LifeOS repository.
  - Upstream outage preservation did not detail how requests are identified, preserved, and retried without causing duplicate state mutations.
  - Dynamic custom signal registration did not specify what happens if schema registration fails or how retry avoids data loss.
- **Correction in V2.3:**
  - Refined the taxonomy into an **Eight-Tier Taxonomy**, introducing `[STAT-CONV]` (statistical conventions like Gaussian 2.5 Z-score) and `[LIT-BASE]` (literature baseline like 21-day habit decay), and accurately reclassifying `LifeStateWeights` as `[PROD-DEF]` (developer product baseline defaults).
  - Defined the **Upstream Outage Preservation Lifecycle**: tags requests with deterministic `requestId`/`turnId`, stores `OutagePreservationRecord` in MongoDB session state on outage, and enforces kernel idempotency deduplication on retry.
  - Defined the **Dynamic Custom Signal Lifecycle**: guarantees zero data loss by persisting novel observations immediately into `DailyLog.customSignals` before asynchronous schema registration in `SignalDefinitionModel`, with idempotent re-ingestion tokens.
  - Added the **Decision Correctness Matrix** in Section 9.2 to explicitly penalize eager execution and reward correct clarification and rejection.
